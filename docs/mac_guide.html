Private Air-Gapped AI Workspace on Mac with Codex CLI

A practical Apple Silicon workflow for fine-tuning a local OSS model on private workspace-derived data, serving it locally, and using it safely through Codex CLI.

1. What This Setup Does

This setup gives you a strong local-only workflow:

  • Codex CLI runs on your Mac
  • the model is served locally
  • your workspace is scoped to specific directories
  • sandboxed shell commands can be denied network access
  • you can fine-tune a local OSS model on private workspace-derived data
Important: --oss does not by itself create a true air gap. A true air-gapped workflow also requires web search off, no remote MCP usage, and host-level network isolation.

2. Core Concepts

Codex CLI

Codex CLI is the local terminal agent. It reads, edits, and operates on files inside the workspace you expose to it.

--oss

--oss tells Codex to use the local open-source model provider. In the current Codex CLI, the local providers are ollama and lmstudio.

network_access = false

This controls whether sandboxed model-generated shell commands can use the network. It is an important local-only control, but it is not the full air-gap boundary by itself.

Workspace Scoping

Codex does not automatically train itself on your workspace. You give it access to a workspace for the current session:

codex --oss -C ~/SensitivePatent
codex --oss -C ~/SensitivePatent --add-dir ~/ResearchDocs

This is session context, not permanent model learning.

Fine-Tuning

Fine-tuning happens outside Codex. You adapt a local model, serve it locally, and then point Codex at that served model.

3. LoRA and QLoRA

  • LoRA = Low-Rank Adaptation
  • QLoRA = Quantized Low-Rank Adaptation

LoRA trains small adapter weights instead of retraining the full model. QLoRA does the same while keeping the base model quantized to reduce memory usage.

4. Recommended Architecture on Mac

  1. Prepare a base open-source model locally
  2. Convert your private workspace into a supervised fine-tuning dataset
  3. Fine-tune locally with MLX
  4. Fuse or keep the adapter
  5. Serve the resulting model locally through LM Studio or Ollama
  6. Use Codex CLI with --oss and -m to connect to that local model
Boundary: MLX is the fine-tuning tool on Mac. LM Studio or Ollama is the local model server Codex connects to.

5. Installation

Install Codex CLI

brew install --cask codex
codex --version

Install Python and a Virtual Environment

python3 -m venv ~/.venvs/mlx-ft
source ~/.venvs/mlx-ft/bin/activate
python -m pip install --upgrade pip

Install MLX-LM

pip install "mlx-lm[train]"

Install a Local Model Server

Install either LM Studio or Ollama. Codex currently expects the local OSS model to be served through one of these providers.

6. Prepare Before Disconnecting from the Network

If you want a strict air-gapped workflow, download everything first while still online:

  • Codex CLI
  • Python packages
  • the base model
  • LM Studio or Ollama

Only after all dependencies are present should you disconnect the Mac from the network.

7. Choose a Base Model

Start with a manageable instruct or coding model. Typical choices are a 7B model or a 14B model. Use larger models only if your Mac has the memory headroom.

8. Prepare the Fine-Tuning Dataset

Do not point the trainer at a folder and expect it to learn the repo automatically. Fine-tuning requires a curated dataset of examples.

Recommended Format

{"messages":[
  {"role":"system","content":"You are an expert assistant for this private codebase."},
  {"role":"user","content":"Explain how the job scheduler works."},
  {"role":"assistant","content":"The scheduler coordinates queued tasks by..."}
]}

Create a Dataset Directory

mkdir -p ~/airgap-ft/data

Suggested files:

  • ~/airgap-ft/data/train.jsonl
  • ~/airgap-ft/data/valid.jsonl
  • ~/airgap-ft/data/test.jsonl

Quality Rules

  • remove secrets you do not want reproduced
  • prefer clean examples over raw volume
  • keep response style consistent
  • hold out test examples for evaluation

9. Fine-Tune Locally with MLX

mlx_lm.lora \
  --model /path/to/base-model \
  --train \
  --data ~/airgap-ft/data \
  --iters 600 \
  --batch-size 1 \
  --num-layers 4 \
  --adapter-path ~/airgap-ft/adapters

This trains a LoRA adapter locally and stores it in ~/airgap-ft/adapters.

10. Test the Adapter

mlx_lm.generate \
  --model /path/to/base-model \
  --adapter-path ~/airgap-ft/adapters \
  --prompt "Explain how the scheduler works in this private codebase."

Compare outputs against held-out examples and known-good answers before deploying.

11. Fuse the Model for Serving

mlx_lm.fuse \
  --model /path/to/base-model \
  --adapter-path ~/airgap-ft/adapters \
  --save-path ~/airgap-ft/fused_model

This produces a deployable fused model artifact.

12. Serve the Fine-Tuned Model Locally

The practical path is:

  1. load the fused or adapted model into LM Studio or Ollama
  2. start the local server
  3. note the served model identifier

13. Use the Fine-Tuned Model with Codex CLI

codex --oss --local-provider lmstudio -m your-finetuned-model -C ~/SensitivePatent
codex --oss --local-provider ollama -m your-finetuned-model -C ~/SensitivePatent

--oss selects the local OSS provider, --local-provider selects LM Studio or Ollama, -m chooses the served model, and -C sets the primary workspace.

14. Recommended Secure Codex Settings

codex \
  --oss \
  --local-provider lmstudio \
  -m your-finetuned-model \
  -C ~/SensitivePatent \
  --sandbox workspace-write \
  --ask-for-approval on-request
model_provider = "oss"
oss_provider = "lmstudio"
model = "your-finetuned-model"
approval_policy = "on-request"
sandbox_mode = "workspace-write"
web_search = "disabled"

[sandbox_workspace_write]
network_access = false

15. Important Security Boundaries

  • --oss means local model provider
  • network_access = false means sandboxed shell commands cannot use the network
  • neither of those alone guarantees a true physical air gap

For a true air-gapped workflow, also isolate the host machine, disable remote integrations, and avoid any sync tool that can move data off the device.

16. Fine-Tuning vs Retrieval

Fine-tuning is best for style, behavior, and transformation habits. Retrieval is better for frequently changing files and exact recall from current documents.

17. Minimal End-to-End Workflow

  1. Install Codex CLI, MLX-LM, and a local model server
  2. Download the base model while still online
  3. Build a clean JSONL dataset from the private workspace
  4. Disconnect the Mac from the network
  5. Fine-tune with MLX LoRA or QLoRA
  6. Test the adapter
  7. Fuse or package the model
  8. Serve it locally through LM Studio or Ollama
  9. Launch Codex with --oss -m ...
  10. Work inside the scoped private workspace

18. Example Session

codex \
  --oss \
  --local-provider lmstudio \
  -m patent-coder-private-v1 \
  -C ~/Documents/SensitivePatent \
  --add-dir ~/Documents/PatentResearch \
  --sandbox workspace-write \
  --ask-for-approval on-request

Inside Codex, use /status to verify the model, sandbox settings, and writable roots.

19. Final Takeaway

The correct mental model is:

  • Codex scopes and uses your local workspace
  • MLX fine-tunes a local model on a curated dataset derived from that workspace
  • LM Studio or Ollama serves the resulting model locally
  • --oss and network_access = false support a strong local-only workflow
  • host-level isolation is still required for a true air gap
